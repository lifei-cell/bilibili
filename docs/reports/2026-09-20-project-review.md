# Bilibili Cloud 项目亮点与提升建议

复核日期：2026-09-20；提交基线：`dec8aab`。当前工作区包含既有暂存和未暂存改动，本文不把这些改动算作稳定交付能力。

详细的业务不变量、实现取舍、答辩表达和分阶段任务见 [项目亮点与开发计划详细版](./2026-09-20-project-highlights-development-plan-detailed.md)。

## 结论

项目已经超过“中间件拼装型 Demo”，最有价值的部分是围绕视频转码、消息投递和搜索索引构造了明确的业务不变量、失败窗口、恢复机制与本地验证证据。当前定位应是“可靠性设计较完整、具备真实容器演练的本地视频平台”，不能描述为生产系统、生产容量或 Exactly Once。

## 项目亮点

| 亮点 | 关键实现 | 可证明的价值与边界 |
| --- | --- | --- |
| 上传到播放的完整媒体链路 | 秒传、分片续传、MinIO、RocketMQ、FFmpeg 多档 HLS；数据库租约、`claim_generation`、令牌及独立 `attempt-*` 前缀阻止旧 Worker 覆盖新结果；首档发布后高档位可补偿，失效产物可清理。 | 双 Worker 崩溃接管和低清持续可读已有本地容器证据；MySQL 与 MinIO 之间仍是最终一致，尚未覆盖 FFmpeg 错误和网络超时注入。 |
| 可恢复的异步消息链路 | 通用 Outbox、Inbox 幂等、有限重试、应用 DLQ 和重放；转码任务另有持久化领取与超时恢复。 | 能清楚解释重复投递、消费者失败和恢复流程；语义是至少一次，不是 Exactly Once。 |
| 实时弹幕与异步落库 | Netty WebSocket 房间广播、Redis Pub/Sub 跨实例、RocketMQ 异步持久化，一次性 Ticket 避免令牌进入 URL。 | 真实 Compose E2E 覆盖核心链路；Redis Pub/Sub 不提供离线可靠投递。 |
| 可重建的搜索读模型 | MySQL 为事实源，Canal 驱动 ES；影子索引分页构建、对账、Alias 原子切换和旧索引回退；MySQL 命名锁协调多实例，晚到事件回源 MySQL 防止索引回退。 | 双 Canal、20 次更新的单次演练全部消费并在 2.659 秒追平；该结果是短时本地证据，不是容量 SLO。 |
| 分层工程验证 | Maven/JaCoCo/Testcontainers、Vitest/Playwright、Compose E2E、故障演练、k6、资源与 MQ 门禁形成分层证据。 | 历史报告记录九模块 94 个测试、P0/P1/P2 本地门禁通过；尚无本轮远端 CI 或目标部署环境证据。 |
| 可观测与运维入口 | 请求 ID/Trace ID、结构化日志、Prometheus 指标、Grafana/Loki/Tempo、DLQ 管理与索引对账入口。 | 具备定位问题的工程基础；仍需用真实告警闭环、备份恢复和恢复时间证明运维能力。 |

面试或简历应优先讲三条：转码租约与崩溃接管、Outbox/Inbox 的至少一次与幂等、ES 影子索引的多实例切换。每条都按“业务不变量 → 失败窗口 → 恢复机制 → 验证证据”展开，不要只罗列技术栈。

## 进一步提升

| 优先级 | 模块与动作 | 验收标准 |
| --- | --- | --- |
| P0 | 交付基线与远端 CI：先收敛当前工作区改动，使 `master` 的后端、前端、浏览器旅程、Compose E2E 和发布门禁在远端可重复运行，并保留报告产物。 | 干净提交绑定 SHA；远端流水线全绿；测试数、跳过数、环境和报告可追溯。本地或历史报告不能替代远端结果。 |
| P0 | 容量与 Gateway 瓶颈：针对约 300 HTTP RPS 时 Gateway CPU 配额峰值 98.97% 做 Trace/火焰图和依赖耗时分解，再在目标配额、固定数据集下做持续压测。 | 至少 15–30 分钟稳定运行，记录吞吐、P95/P99、错误率、CPU/内存、连接池和 MQ 曲线；明确饱和点与降级策略，不把 30 秒本地结果外推为生产容量。 |
| P0 | 灾备与安全交付：补 MySQL/MinIO 备份恢复、密钥注入、TLS/CDN、依赖/镜像/Secret 扫描。Compose 的演示默认凭据只允许本地使用。 | 在隔离环境从备份恢复元数据和对象，验证播放及搜索对账，记录 RTO/RPO；生产配置无默认密钥，CI 对高危漏洞和泄密有门禁。 |
| P1 | 转码故障矩阵：增加 FFmpeg 非零退出、进程挂起、MinIO 超时/部分写入、消息重复和 Worker 网络隔离。 | 每类故障都有自动化演练；已发布低清保持可播，旧代次不能提交，重试耗尽可查询，孤儿对象最终清理。 |
| P1 | 搜索重建产品化：将并发重建从一个请求返回 500，改成异步任务和明确的冲突/进度状态；固定数据规模重复量化切换。 | 并发请求返回可解释的 202/409；支持进度、失败原因、回滚和审计；多轮报告给出锁等待 P95/P99、积压峰值、追平时间与搜索可用性。 |
| P1 | 前端性能与覆盖面：对约 607 KB 的 `VideoView` 产物做路由/播放器拆包；当前高覆盖率只统计少量核心文件，应扩展认证、上传页、播放页、管理页和异常态。 | 关键首屏与播放器 chunk 低于约定预算；覆盖率口径包含核心页面；桌面和移动视口覆盖登录、上传恢复、播放、弹幕重连与管理员流程。 |
| P2 | 业务差异化：可靠性收口后再补一条完整业务主线，例如创作者数据看板或可解释的基础推荐，不再堆新的基础设施。 | 有明确用户问题、数据口径、离线/在线指标、降级路径和端到端验收；能说明它为何比新增中间件更有业务价值。 |

不建议现在直接引入 Kubernetes、更多 MQ 或复杂推荐平台。先把远端交付、持续容量、灾备安全和故障矩阵做实，投入产出比更高。

## 本轮验证

- `mvn -s .mvn/settings.xml --batch-mode --no-transfer-progress test`：9 模块成功，31 份 Surefire 报告共 90 个测试，失败/错误/跳过均为 0。
- `npm run quality`：通过；5 个测试文件、14 个测试通过；Statements 95.89%、Branches 87.77%、Functions 96.87%、Lines 100%；类型检查和生产构建通过。
- `npm run test:e2e`：2 条 Playwright 旅程通过，覆盖上传/发布/播放/弹幕重连及 401/断点续传恢复。
- `mvn ... clean verify`：本轮未通过完整门禁，阻断原因为 Docker Desktop Linux Engine 管道不存在，`UserApiIT` 的 Testcontainers 无法启动；这不是应用断言失败，也不能记为本轮验证通过。
- 历史已提交报告记录本地 P0 发布复验、P1 双 Worker/双 Canal 演练和 P2 分场景短时基线通过；其环境与边界继续以各报告为准。
