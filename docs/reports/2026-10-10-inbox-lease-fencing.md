# Inbox 租约接管防护

## 问题与复现

旧实现只有 `PROCESSING` 状态条件，完成和失败回写未校验领取者。真实 MySQL 8.4 回归依次执行领取、强制过期、另一消费者接管、旧消费者回写：原本应保持 `PROCESSING` 的新租约分别被旧消费者改成 `SUCCEEDED` 和 `FAILED`。修复前两条断言失败，未跳过测试。

仅给完成回写加 token 不能阻止旧回调执行数据库业务，所以本次同时处理了业务事务与接管的互斥边界。

## 实现

- Flyway V9 增加 `claim_token` 和 `claim_generation`；每次接管更换 token 并增加代次。
- 成功和失败回写同时校验消息身份、状态、token、代次和租约有效期。
- `MessageInboxLeaseGuard` 在独立事务中用 `SELECT ... FOR UPDATE` 保护业务回调；接管不能越过正在执行的数据库事务。成功标记失败时事务回滚，部分业务写入不会提交。
- 重试各自使用独立事务；最终失败标记和 DLQ 记录同事务提交。租约失效后立即退出，不重试旧业务、不改新领取者的 DLQ。
- 正在处理的竞争投递抛回 Broker；只有已经成功的重复投递直接确认。
- 弹幕可靠消费在调用线程内落库，与统计标脏和 Inbox 共享事务。事务外调用仍支持队列批量写入。

## 验收范围

定向验证包括 7 条执行器单测、9 条真实 MySQL 测试、2 条弹幕写入测试，全部通过，零失败、零错误、零跳过：

1. 旧消费者的成功和失败回写都被拒绝，新 token 保留。
2. 过期但尚未接管的消费者不能写业务或完成状态。
3. 新消费者提交后，旧回调不能覆盖业务值或修改 DLQ。
4. 业务执行期间租约失效，数据库副作用回滚。
5. 并发接管等待旧事务回滚，非幂等计数只有新消费者的一次提交。
6. 重试前的部分业务写入回滚；失败记录、成功去重和 DLQ 恢复正常。
7. V8 到 V9 升级保留成功记录，过期旧记录可重新领取。
8. 弹幕事务路径不再等待后台 flush，原事务外批量路径仍可用。

完整后端验收使用 `mvn -s .mvn/settings.xml --batch-mode --no-transfer-progress verify`：9 个 Reactor 项全部成功，共 118 个测试，零失败、零错误、零跳过，业务模块覆盖率门禁通过。

真实 Compose 验收使用本次构建的新镜像运行 `scripts/e2e/reliability-e2e.ps1 -SkipBuild`，上传、转码、发布、播放、搜索、互动、弹幕、创作者身份隔离、自动统计及迟到数据重算全部通过。验收后脚本清理测试数据并停止启动的服务。该次未启用 `-RunFaultDrill`，未运行 k6 持续压测。

本地原始记录：`.inbox-lease-reproduction.log`（修复前两条失败）、`.inbox-lease-focused.log`、`.inbox-lease-verify.log`、`.inbox-lease-compose.log`；机器可读业务报告为 `loadtest/results/inbox-lease-20261010/compose-e2e.json`，`passed=true`、`error=null`。这些生成文件由现有忽略规则排除，源码和本报告纳入提交。

## 运行边界

这次保证的是数据库业务、Inbox 和 DLQ 的事务边界。Redis/ES 等外部请求不能由数据库回滚撤销，仍需其自身幂等和恢复机制；数据库连接丢失后的外部在途请求不属于本次严格原子性保证。

可靠弹幕消费改为事务内逐条写入，会减少批量写入收益。默认 60 秒期限内不能完成的业务应调整租约，且要关注事务占用连接的时间与 MQ 积压。部署先退出所有旧版消费者，再迁移并启动新版，避免旧 SQL 越过新防护。

本次结果属于本地 MySQL/后端验收，不代表远端 CI、生产部署或生产容量验证。
